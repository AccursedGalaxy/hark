Org chart · how the agents work

Inside a hark orchestration

hark runs a project as a small, role-playing company of Claude Code sessions. A human sets direction. A PM-head owns the plan and delegates. A team of worker agents — each in its own isolated git worktree — does the building. Everyone is the same model; the role is carried entirely by the briefing each one receives.

Roles are a palette, not a fixed roster — the PM spawns what a task needs and skips what it doesn't. Each worker gets its own git worktree + branch, so two agents never collide on the working tree.

The roster

What each role does & when it's "done"

Every agent is an ordinary Claude Code session driven over tmux. Its role is a charter — a mission, a way of working, and a definition of done — delivered as the first message it receives.

PM-head reports to → Human manages → all workers

A persistent, project-scoped product manager — a role, not a task with an end. PLAN.md is its durable brain; a fresh session resumes the role by re-reading it.

How it works

  • Pure PM, read-only on the tree — a PreToolUse hook denies any edit / write / tree-mutating git against the project. Only PLAN.md and .hark/ are writable. This is enforced, not a guideline.
  • Picks the cheapest path per item — apply a one-liner the human runs, paste a small patch in chat, or dispatch a worker for substantial / parallel work.
  • Works from summaries, never transcripts — context discipline is make-or-break: a PM that slurps transcripts runs out of context and the orchestration dies.
  • Never lands — it prepares ready branches and opens PRs; the human owns the final merge.

Never "done"

  • An ongoing role — it emits no completion marker; it just keeps the plan honest and the team moving.
Researcher reports to → PM-head

Maps the problem space and produces a concrete findings brief.

Charter

  • Read before you write — explore the code, docs, and prior art.
  • Produce a brief, not code: files that matter, constraints, recommended approach with trade-offs.
  • Surface risks & edge cases the Coder and Tester will hit.
  • Cite concrete file:line references so downstream roles don't re-derive the work.

Definition of done

  • A brief covers files, constraints, approach, risks, and open questions.
  • Every claim is backed by a file:line or tagged "unverified".
  • The approach is specific enough that a Coder could start immediately.
Coder reports to → PM-head

Implements the change on an isolated branch, in small commits.

Charter

  • Work in this worktree only — never touch other agents' trees or the human's checkout.
  • Match the surrounding code: naming, comment density, idioms.
  • Small, reviewable commits; keep the build green as you go.
  • Follow the Researcher's brief if there is one; deviate only with a recorded reason.

Definition of done

  • Change implemented; project builds / type-checks cleanly.
  • Work committed with descriptive messages.
  • No scaffolding, dead code, or unrelated edits left behind.
  • A short change summary recorded for the Reviewer.
Tester reports to → PM-head

Proves the change works and guards it with tests.

Charter

  • Write and run tests for the change, including the Researcher's flagged edge cases.
  • Use the project's existing framework & conventions — discover them, don't impose.
  • Run the full suite, linter, and type-checker; report actual output, not a summary.
  • A red test that exposes a real bug is a success — report it, don't paper over it.

Definition of done

  • Tests cover the change and its known edge cases.
  • Full suite + linter + type-checker run, real results reported.
  • Any failure is fixed or escalated with a precise reproduction.
Documenter reports to → PM-head

Records what changed for humans and the next session.

Charter

  • Update the user- and developer-facing docs the change touches.
  • Keep PLAN.md honest — move shipped work, drain the inbox lines this change resolves.
  • Write for a cold-start session: explain the why, not just the what.
  • Document only what the Coder and Tester actually produced — never invent behaviour.

Definition of done

  • Affected docs are updated and accurate.
  • PLAN.md reflects reality; inbox triaged.
  • No doc claims behaviour the code doesn't have.
Reviewer reports to → PM-head

Adversarially reviews the result before it merges.

Charter

  • Review the diff against the goal and the brief — assume there's a bug until convinced otherwise.
  • Check correctness, edge cases, security, and that tests really exercise the change.
  • Verify the Coder's claims by reading (and cheaply running) the code — don't trust the summary.
  • Produce a prioritized list: blocking / should-fix / nit.

Definition of done

  • Full diff reviewed for correctness, edge cases, security.
  • Findings recorded with file:line references.
  • A clear verdict: APPROVED or CHANGES-REQUESTED with the blocking items.

Communication

How a report travels up the chain

A worker never "calls a meeting." It prints a bracketed marker token at the end of its final message; the autonomy controller reads it off the transcript and routes the result up to the PM — who works from a compact notification, never the raw transcript.

The three signals a worker can raise

[[HARK:DONE]]
Finished and self-reviewed against the definition of done. Preceded by a 2–4 line summary of what it produced.
[[HARK:BLOCKED]]
Genuinely stuck — needs a human decision. Preceded by the specific question. The PM escalates it to the human.
[[HARK:HANDOFF]]
Work is ready for another role (e.g. Coder → Reviewer). Preceded by the handoff summary that role will need.
1
Briefing delivered
Once a worker's session is past its trust prompt, the controller sends its role charter as the first message — over the same tmux send-keys path a human uses. Lifecycle flips to running.
2
Self-review loop
If the worker ends a turn without a marker, the controller nudges it back toward its definition of done — up to 3 times, then escalates to blocked for a human.
3
Worker → PM notification
On a terminal marker the PM is woken exactly once with a compact note: role, branch, marker, diffstat, and commit count — plus the summary. Never the transcript.
4
The newsroom
At the top of each PM turn, a "TEAM NEWS since your last turn" block is injected — a filtered, time-ordered feed of every worker that hit done / blocked / handoff / failed across the project's live orchestrations. The PM triages: surface to the human now, or note it to PLAN.
5
Routing the result
A blocker always pages the human. An advance (done/handoff) is pulled in via the newsroom while the human is chatting — or, if the human is quiet and the dial allows, the PM is pushed a single turn to move the pipeline forward on its own. It never lands work.

State

A worker's lifecycle

pending→ spawning→ running→ blocked review done failed stopped cancelled

pending → record created · spawning → worktree ready, session launching · running → working toward its definition of done. The terminal states (blocked / done / failed / stopped / cancelled) are end states — a finished worker is reaped (its process killed) but its worktree and branch are kept so the PM can still read the work.

Safety

Guardrails that keep autonomy safe

🌳

Worktree isolation

Every agent — workers and the executor head — gets its own git worktree + branch. They share one object store but never one live tree, so parallel agents can't collide.

🔒

Read-only PM

A PreToolUse hook runs every PM tool call through a guard that denies writes to the source tree. Only PLAN.md and .hark/ are writable — "pure PM" is a system property, not trust.

⚡

Runaway circuit-breaker

A worker that repeats identical no-op commands without advancing its branch is tripped to blocked and reaped — defending against the token-burning spiral, independent of the autonomy dial.

🛑

Manual stop

hark agent stop <id> SIGTERMs a worker's session — idempotent and zombie-safe — while keeping its worktree so the work survives.

🙋

Human owns landing

The PM prepares branches and opens PRs but never merges into the working tree. The final fast-forward / merge stays the human's, at a moment they choose.

📋

PLAN.md as the brain

Durable decisions live in PLAN.md via targeted edits (concurrent-session safe), so any fresh session resumes the project by re-reading it — not by trusting a chat history.

Autonomy

The dial the human controls

A per-project setting governs only how far the PM advances the pipeline on its own while the human is quiet. Blockers always escalate to the human, and the PM never lands work — at any level.

L0
Propose

Only suggests plans & diffs; the human dispatches and applies everything.

L1
Assisted

Dispatches on the human's approval; advances on the human's nod.

L2 default
Supervised-auto

When idle, autonomously advances the pipeline (done → next stage, spawn a tester, open a PR). Still escalates blockers, never lands.

L3
Background

Runs whole features end-to-end while the human is away.

Action surface

How the PM acts — the hark CLI

The PM does everything through one thin CLI (already on its PATH, auto-targeting its project). It dispatches, harvests, and prepares PRs — but never checks a branch out against the project root.

hark orch status # one compact line per worker: role / lifecycle / branch / diffstat / turns hark agent spawn <role> --task "…" # spawn a worker with a charter; prints its agentId (--depends-on <id>) hark agent send <id> "…" # steer / message a running worker hark agent brief <id> "<task>" # assign the worker its next task hark agent diff <id> [--stat|--full] # worker branch vs base hark agent log <id> # recent commits on the worker branch hark agent summary <id> # the worker's full terminal marker text (survives reaping) hark agent stop <id> # SIGTERM the worker, keep its worktree hark pr <id> [--title "…"] [--base <ref>] # push the branch + open a PR — the human still merges it

For a genuine branch collision the PM doesn't merge by hand — it dispatches an integrator worker (hark agent spawn coder --task "merge A into B, resolve conflicts"), because conflict resolution is judgment and stays in an isolated worktree. With no remote, hark pr degrades gracefully to "branch ready, here's the diff."

It describes only behaviour present in the current code.
